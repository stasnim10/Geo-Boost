## PROMPT 1 — Make billing correct end to end

---

You are working on Show me on AI. Fix subscription activation so that a user who completes Stripe checkout has their paid plan reflected everywhere within seconds, and so that any failure in that chain is loud instead of silent.

**Stack facts — do not rediscover these:**
- Identity is Clerk. Subscription state lives in the `subscriptions` table keyed on `clerk_user_id`, with columns `plan`, `status`, `stripe_customer_id`, `current_period_end`, `updated_at`. Plan values are `fix`, `monitor`, `grow`.
- Stripe is currently in **test mode**.
- The webhook handler is at `/api/stripe/webhook`. Stripe had been configured to POST to `/api/webhook` and was getting 404s; an alias now exists.
- The webhook route is already mounted with `express.raw({ type: 'application/json' })` before `express.json()`. **This is correct. Do not change it.**
- The gated feature endpoint is `/api/geoboost/optimize`.

**Known broken behaviour to fix:**
- After a successful payment, `/success` renders "Your **Free** plan is now active."
- Paid features stay locked after payment.
- `/results` shows a "Create a free account to save these results" banner while the navigation on the same page shows the user signed in. Two parts of one screen disagree about whether anyone is logged in.

### Work to do

1. **Canonical endpoint.** Treat `/api/stripe/webhook` as the only supported webhook path. Keep the `/api/webhook` alias for now, but log a warning whenever it is hit, including the Stripe event id, so we can see when the Stripe dashboard config has actually been corrected. Do not delete the alias in this change.

2. **Carry identity through checkout.** When creating the checkout session, set `client_reference_id` to the Clerk user id, set `metadata` to `{ clerkUserId, plan }`, and set `success_url` to include `session_id={CHECKOUT_SESSION_ID}`.

3. **Harden the webhook handler.**
   - Handle `checkout.session.completed`, `customer.subscription.updated`, and `customer.subscription.deleted`.
   - Resolve the user in this order: `client_reference_id`, then `metadata.clerkUserId`, then an existing `stripe_customer_id` match. Email matching is a last resort only, and must log a warning when used.
   - Upsert the `subscriptions` row with plan, status, `stripe_customer_id` and `current_period_end`.
   - **Assert on the result.** If the write affects zero rows, throw and return a non-2xx so Stripe retries. A silent 200 on a failed write is the specific bug we are eliminating.
   - Make the handler idempotent by recording processed Stripe event ids and short-circuiting on repeats. Stripe retries, and a retry must not double-provision or reset a plan the customer has since changed.
   - Log, for every event: event id, event type, resolved `clerk_user_id`, and rows affected.

4. **Add `GET /api/billing/status`.** Authenticated via Clerk, returns `{ plan, status, currentPeriodEnd }` for the current user, read server-side from the database. The client must never determine its own plan.

5. **Rewrite the success page.** Read `session_id` from the URL, have the server retrieve that checkout session from Stripe, then poll `/api/billing/status` for up to about 15 seconds. Three states, and these exact strings:
   - While confirming: **"Payment received. Confirming your plan…"**
   - On confirmation: **"Your {Plan} plan is active."** — using the plan actually purchased, followed by one single next action that the plan just unlocked.
   - If still unconfirmed after the polling window: **"Payment received. Activation is taking a little longer than usual."** — reassure the charge is safe, offer a refresh, give a contact route, and log this server-side as an alert condition, because a customer seeing it means a webhook is failing right now.

   The success page must never print a plan name it has not confirmed with the server. Never grant access because a browser arrived at `/success` — anyone can type that URL.

6. **One entitlement module.** Define the plan constants and the entitlement check once, in one module, with lowercase values, and import it everywhere. No inline plan-string comparisons in components.

7. **Distinguish 401 from 403 in the UI.** Users must never see the raw words "Unauthorized" or "Forbidden".
   - `401` means the Clerk session is missing — an identity problem. Show: **"Your session expired. Sign in again to continue."** with a sign-in button.
   - `403` means signed in but the plan is inactive or not entitled — a billing problem. Show: **"Content rewriting is part of the Fix package."** naming the plan that unlocks it, linking directly to checkout.

8. **Add a Current plan card to the dashboard.** Plan, status, renewal date, and a link to manage billing. One place where the truth is visible in two seconds.

9. **One client session source of truth.** Consumed by every component, invalidated and refetched after sign-in and after returning from checkout. The "Create a free account" banner appearing on a page where the nav shows a signed-in user must stop happening as a consequence of this — if it doesn't, there is still more than one source of truth and the job isn't done.

### Do not

- Do not change the `express.raw()` / `express.json()` mounting order.
- Do not redesign any UI beyond the specific states and messages above.
- Do not change prices, plan names, or plan tiers.
- Do not refactor unrelated code.
- Do not remove the `/api/webhook` alias yet.

### Definition of done — show me each of these

Do not report this as complete until you can show:

1. A **fresh** test user (not an existing account, which may carry state that masks the bug) completing checkout with card `4242 4242 4242 4242`, on a session id beginning `cs_test_`.
2. The Stripe **test-mode** dashboard showing `checkout.session.completed` against `/api/stripe/webhook` with a **200**.
3. The resulting database row:
   ```sql
   SELECT clerk_user_id, plan, status, stripe_customer_id, current_period_end, updated_at
   FROM subscriptions ORDER BY updated_at DESC LIMIT 5;
   ```
   showing `status = active` and the purchased plan.
4. `/api/geoboost/optimize` returning **200** for that user.
5. The success page having shown the confirming state and then the correct plan name — not "Free".
6. The same webhook event replayed from the Stripe dashboard leaving the database state unchanged.

Also confirm which of these four are in agreement, since a mismatch produces a payment that looks successful and an event that appears never to have fired: the secret key prefix (`sk_test_` vs `sk_live_`), the checkout session prefix (`cs_test_`), the Stripe dashboard mode you are inspecting, and which endpoint's `whsec_` signing secret is deployed.

Republish production before testing. A route fix in the workspace does nothing for Stripe, which talks to the live deployment.

## PROMPT 2 — Navigation and confirmed defects

**Only paste this after Prompt 1's verification block passes.**

---

You are working on Show me on AI. This task is navigation integrity and a set of specific defects observed in production. No redesign, no new features — make what exists behave correctly.

### Navigation

1. `/audit` returns a 404 whose body reads **"Did you forget to add the page to the router?"** — a developer message shipped to production. Replace the 404 handler with a real not-found page that offers a way back.

2. The nav renders five items — Audit, Optimizer, Fix, Compare, Pricing — but only three destinations exist. `Audit` links to `/` and `Fix` resolves to the homepage. Either give Audit and Fix real destinations, or remove them from the nav. A nav item that returns the user to the page they are already on is worse than no nav item.

3. Sign In and Get Started appear on the homepage but are absent from `/pricing`, `/compare` and `/optimizer`. The signup button disappears on the page where people decide to buy. Render the auth controls — signed-out CTAs or the signed-in account menu — from one shared layout component present on every page.

### Defects

4. **Strip tracking parameters from displayed URLs.** The results page prints the audited URL raw, so a Google click id renders as the headline:
   `https://perfumania.com/?srsltid=AfmBOorUyfh4OVmw5XvhOaiNEREbxhArAx18WcHPcu8Bl_-eM--8yUNf`
   and repeats four times down the page. Display the hostname — `perfumania.com` — while keeping the full URL for the actual fetch. Strip `srsltid`, `gclid`, `fbclid`, and all `utm_*` parameters.

5. **Fix optimizer content extraction.** Auto-fetch currently scrapes the whole DOM. The 8,000 characters pulled from Perfumania are largely "Pause slideshow", "Close modal", "Forgot your password?" and the entire login form. Trimming to 6,000 then preserves the boilerplate and discards the real copy — so the rewriter is being fed garbage. Extract main content properly: remove `nav`, `header`, `footer`, `script`, `style`, forms, and modal/dialog containers before trimming, and trim from the end of the extracted body rather than blindly truncating the raw scrape.

6. **One call to action per screen.** The results page currently offers `$149/mo`, `$49 quick-fix`, and `$49 fix files` within two screens of each other. Pick the primary action per section and demote the rest to a text link.

7. **Explain the score relationship.** The results page shows three gauges — 14 overall, 42 content depth, 55 readability — with no stated relationship. A reader immediately asks why the headline number sits below both of its components. Either show the weighting that produces the overall score, or show a single number.

8. **Label the revenue estimate honestly.** The "$5.8k estimated monthly revenue going to competitors" figure is currently footnoted "based on typical market data". Make the method inspectable — an expandable "How is this calculated?" that shows the inputs and the arithmetic — or present it as a range. A precise-looking number with an unexplained derivation is the weakest claim on an otherwise strong page.

### Do not

- Do not change the audit scoring logic, the issue-detection prompts, or the written analysis. That content is the strongest part of the product and is not in scope.
- Do not change pricing or plan structure.
- Do not restyle pages beyond what these fixes require.

### Definition of done

Every nav item resolves to a distinct working page; no route returns a developer error message; auth controls are present on every page in both signed-in and signed-out states; the results page displays a clean hostname; and a fresh optimizer auto-fetch on a content-heavy commercial site returns readable body copy with no navigation, modal, or login-form text in it.
